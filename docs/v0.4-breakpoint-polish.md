# v0.4 Breakpoint Polish

This document describes the second Zero-CPU v0.4 debugger usability feature.

## Goal

Studio already had basic breakpoint controls:

```text
BP PC input
Add BP
Clear BP
Run stops when PC reaches a breakpoint
```

This patch improves the usability and visibility of that breakpoint behavior.

## Improvements

## 1. Sorted Breakpoint List

Breakpoints are now kept sorted after insertion.

This makes the breakpoint list easier to scan:

```text
[0] PC = 536
[1] PC = 656
[2] PC = 920
```

## 2. Duplicate Breakpoint Message

Adding the same breakpoint twice no longer silently does nothing.

Studio now reports:

```text
Breakpoint already exists at PC=656
```

## 3. Current PC Marker

The breakpoint view marks a breakpoint that matches the current PC:

```text
[1] PC = 656  <current>
```

This makes it clearer why `Run` stopped.

## 4. Breakpoint Hit Status

When `Run` stops at a breakpoint, Studio records the hit state.

The State View can show:

```text
Last Breakpoint Hit = PC 656
```

This makes breakpoint behavior visible outside the trace log.

## 5. Reset Clears Breakpoint Hit State

Reset clears:

```text
breakpoints
last breakpoint hit flag
last breakpoint hit PC
```

## Why this matters

v0.4 focuses on debugger usability.

A debugger is not only about showing instruction details. It also needs basic
navigation control.

Breakpoint polish helps answer:

```text
Where did execution pause?
Did I add this breakpoint already?
Which breakpoint is the current one?
Was the last run stopped by a breakpoint?
```

## Current Limitations

This is still a small breakpoint layer.

Known limitations:

```text
- breakpoints are PC-only
- no source-line breakpoint mapping yet
- no temporary breakpoints yet
- no enable/disable per breakpoint yet
- no conditional breakpoints yet
```

Those limitations are acceptable for this patch because source-line mapping is a
larger v0.4 task.
