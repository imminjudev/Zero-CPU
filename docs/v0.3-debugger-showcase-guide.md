# v0.3 Debugger Showcase Guide

This guide explains how to use `examples/debugger_showcase.zasm` to demonstrate the Zero-CPU Studio v0.3 debugger features.

The showcase is designed to prove that Studio can explain instruction execution across four major areas:

```text
ALU Detail
Memory Detail
Stack Detail
Control Flow Detail
```

## Launch Flow

From the repository root:

```bat
cd /d D:\Zero-CPU
.\build\Debug\zero_studio.exe
```

Studio should default to:

```text
examples\debugger_showcase.zasm
examples\debugger_showcase.zbin
```

Recommended flow:

```text
Load Source
Assemble
Load BIN
Step
```

If relative paths fail, use absolute paths:

```text
D:\Zero-CPU\examples\debugger_showcase.zasm
D:\Zero-CPU\examples\debugger_showcase.zbin
```

## What v0.3 Adds

v0.2 added the visual debugger structure:

```text
Visual Datapath Panel
Graphical Datapath Canvas
Pipeline Timeline
Execution Detail Probe
Recent Instruction Trace
Memory Map Viewer
```

v0.3 turns the Execution Detail Probe into an instruction explanation layer:

```text
ALU Detail        lhs / rhs / result / destination
Memory Detail     address / route / value / destination
Stack Detail      stack address / SP movement / value / return address
Control Flow      from PC / to PC / taken / target / return address / vector
```

## 1. MOV Instructions

Example:

```asm
MOV R1, 10
MOV R2, 20
```

What to check:

```text
Visual path:
  PC -> InstructionMemory -> Decoder -> RegisterFile -> Flags -> Writeback

Detail sections:
  ALU Detail = inactive
  Memory Detail = inactive
  Stack Detail = inactive
  Control Flow Detail = inactive
```

Purpose:

```text
MOV proves the basic fetch/decode/writeback path.
```

## 2. ALU Detail

Example:

```asm
ADD R1, R2
```

Expected meaning:

```text
R1 = R1 + R2
```

What to check:

```text
ALU Detail
  Active = true
  Operation = ALU_ADD
  lhs R1 = 10
  rhs R2 = 20
  result -> R1 = 30
```

Good screenshot point:

```text
Datapath Canvas highlights ALU.
Execution Detail Probe shows lhs / rhs / result.
R1 changes from 10 to 30.
```

## 3. Memory Detail

Example:

```asm
STORE [180], R1
```

Expected meaning:

```text
Memory[180] = R1
```

What to check:

```text
Memory Detail
  Active = true
  Operation = MEMORY_WRITE
  address [180] = 180
  route = RAM
  value R1 = 30
```

Good screenshot point:

```text
Memory[180] changes to 30.
Memory Detail shows route = RAM.
Datapath Canvas highlights Memory/MMIO.
```

## 4. CALL Detail

Example:

```asm
CALL double_value
```

What to check:

```text
Stack Detail
  Active = true
  Operation = CALL
  Stack Address = <old SP>
  SP = <old SP> -> <new SP>
  Return Address = <saved PC>

Control Flow Detail
  Active = true
  Operation = CALL
  From PC = <call PC>
  To PC = <function target PC>
  Taken = true
  Target = <function target PC>
  Return Address = <saved PC>
```

Purpose:

```text
CALL is both a stack write and a control-flow transfer.
```

## 5. PUSH Detail

Example:

```asm
PUSH R1
```

Zero-CPU currently uses an upward-growing stack:

```text
PUSH:
  Memory[SP] = value
  SP = SP + 8
```

What to check:

```text
Stack Detail
  Active = true
  Operation = STACK_PUSH
  Operand = R1
  Stack Address = <old SP>
  SP = <old SP> -> <old SP + 8>
  Value = <R1 before PUSH>
```

Good screenshot point:

```text
Memory[old SP] equals the pushed value.
SP increases by 8.
Stack node is highlighted.
```

## 6. POP Detail

Example:

```asm
POP R3
```

Zero-CPU currently does:

```text
POP:
  SP = SP - 8
  value = Memory[SP]
```

What to check:

```text
Stack Detail
  Active = true
  Operation = STACK_POP
  Stack Address = <new SP>
  SP = <old SP> -> <new SP>
  Value = <popped value>
  Destination = R3
```

Good screenshot point:

```text
R3 receives the popped value.
SP decreases by 8.
Execution Detail Probe shows Destination = R3.
```

## 7. RET Detail

Example:

```asm
RET
```

What to check:

```text
Stack Detail
  Active = true
  Operation = RETURN
  Stack Address = <stack read address>
  Return Address = <target PC>
  Target = <target PC>

Control Flow Detail
  Active = true
  Operation = RETURN
  From PC = <ret PC>
  To PC = <return target PC>
  Taken = true
  Target = <return target PC>
  Return Address = <return target PC>
```

Purpose:

```text
RET is reconstructed as both a stack read and a PC transfer.
```

## 8. MMIO Memory Detail

Example:

```asm
STORE [61440], R1
```

`61440` is the DebugOutputDevice MMIO base address.

What to check:

```text
Memory Detail
  Active = true
  Operation = MEMORY_WRITE
  address [61440] = 61440
  route = DebugOutput MMIO
  value R1 = <value>
```

Purpose:

```text
The same STORE instruction can route to normal RAM or MMIO.
The debugger explains the route.
```

## 9. INT 80 Control Flow Detail

Example:

```asm
INT 80
```

What to check:

```text
Control Flow Detail
  Active = true
  Operation = SOFTWARE_INTERRUPT
  From PC = <int PC>
  To PC = <handler PC>
  Taken = true
  Target = <handler PC>
  Vector = 80
  Return Address = <saved return PC>

Interrupt Detail
  Active = true
  Kind = software interrupt
```

Purpose:

```text
INT is both control flow and interrupt-controller behavior.
Control Flow Detail explains the PC transfer and vector.
Interrupt Detail explains the interrupt category.
```

## 10. HALT

Example:

```asm
HALT
```

What to check:

```text
Action = HALT
halted = true
```

Purpose:

```text
HALT proves the program reached its intended end state.
```

## Suggested Portfolio Explanation

```text
Zero-CPU Studio is a visual debugger for a custom virtual CPU.
The v0.3 debugger does more than show register changes.
It reconstructs instruction-level execution detail across ALU, memory,
stack, and control-flow behavior.

For example, an ADD instruction displays lhs/rhs/result,
a STORE displays address/value/MMIO route,
a PUSH displays stack address/value/SP movement,
and a CALL displays target and return address.
```

```text
2. STORE [180], R1

```

## Current Limitations

The v0.3 details are reconstructed from before/after `TraceEvent` snapshots.

Known limitations:

```text
- Label names and final target addresses are not always both available.
- INT/IRET are not yet visualized as a full interrupt frame.
- The debugger does not yet display a full cycle-by-cycle bus transaction log.
- Stack behavior is explained at instruction granularity, not micro-op granularity.
```

These limitations are acceptable for v0.3 because the feature goal is an instruction-level explanation layer, not a full hardware timing simulator.
