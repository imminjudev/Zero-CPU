# Zero-CPU v0.2 Release Notes

Zero-CPU v0.2 focuses on the Studio visual debugger.

This release turns Zero-CPU from a command-line virtual CPU project into a more
explainable virtual computer platform with a visual instruction execution view.

---

## Highlights

```text
Zero-CPU v0.2 adds:
- visual CPU datapath debugging
- pipeline-style instruction explanation
- execution detail probes
- recent instruction trace history
- memory map viewer
- debugger showcase assembly program
- Studio debugger documentation
```

The main goal is to make custom CPU execution easier to see, explain, and
demonstrate.

---

## Project Direction

Zero-CPU is a small virtual computer platform written in C++17.

It includes:

```text
.zasm source
    -> assembler
    -> .zbin virtual binary
    -> binary loader
    -> virtual memory
    -> CPU fetch/decode/execute
    -> ALU / memory / stack / interrupts / syscalls / MMIO
    -> BIO-OS style demo
```

v0.2 builds on that base by adding a visual debugger layer.

---

## New in v0.2: Studio Visual Debugger

### Visual Datapath Panel

Shows the latest CPU trace event in text form.

It displays:

```text
- current instruction
- PC before / after
- stage
- action
- active datapath path
- changed registers
- changed flags
- changed memory
```

This makes the CPU state transition easier to read after every `Step`.

---

### Graphical Datapath Canvas

Adds a graphical CPU datapath view to Studio.

Main visual flow:

```text
PC -> Instruction -> Decoder -> RegisterFile -> ALU -> Flags -> Writeback
```

Additional paths:

```text
Memory/MMIO
Stack
InterruptCtl
```

Active nodes are highlighted based on the latest `TraceEvent`.

---

### Pipeline Timeline

Explains the latest instruction with a pipeline-style view:

```text
FETCH -> DECODE -> EXECUTE -> MEMORY -> WRITEBACK
```

This is not a cycle-accurate pipeline model yet. It is a visual explanation
layer derived from CPU trace metadata.

---

### Execution Detail Probe

Shows focused detail for the latest instruction.

Sections:

```text
- ALU Detail
- Memory Detail
- Interrupt Detail
- Writeback Summary
```

This makes it easier to see whether the current instruction affected the ALU,
memory, stack, interrupt controller, registers, flags, or MMIO path.

---

### Recent Instruction Trace

Shows recent CPU execution history.

Example:

```text
[8]  PC 8 -> 9   | ADD R1, R1      | ALU_ADD
[9]  PC 9 -> 10  | RET             | RETURN
[10] PC 10 -> 11 | STORE [188], R1 | MEMORY_WRITE
[11] PC 11 -> 12 | PUSH R1         | STACK_PUSH
```

This helps explain how the CPU reached the current state.

---

### Memory Map Viewer

Shows where the current PC and SP are located in the Zero-CPU address space.

Important regions:

```text
[0x0000..0x01FF] Low Data / Scratch
0x0200           Binary code base
0x0800           Default stack base
0x0FA0           BIO-OS stack base
0x1000           Default memory size boundary
[0xF000..0xF00F] DebugOutputDevice MMIO
[0xF100..0xF12F] TimerDevice MMIO
```

This is useful for BIO-OS and binary-loading demos because it explains why code,
stack, scratch data, and MMIO live in different regions.

## BIO-OS Status

The BIO-OS demo remains available through:

```bat
.\build\Debug\zero_cli.exe run-os examples\bio_os
```

Current BIO-OS flow:

```text
boot.zasm
    -> debug output
    -> timer configuration
    -> timer enable
    -> timer interrupt
    -> kernel timer handler
    -> user_program_main
    -> syscalls
    -> clean exit
```

This demonstrates:

```text
- boot/kernel/user source separation
- combined BIO-OS assembly generation
- .zbin binary generation
- binary loading into virtual memory
- MMIO debug output
- timer device
- interrupt handling
- INT 80 syscall convention
```

## Known Limitations

v0.2 is still an early visual debugger.

Known limitations:

```text
- The graphical datapath canvas shows the latest instruction only.
- Pipeline timeline is explanatory, not a cycle-accurate CPU pipeline.
- ALU input operands are not yet captured explicitly in TraceEvent.
- Source-line mapping is still limited.
- Memory inspection is not yet an interactive grid.
- Breakpoint UI is still basic.
```

These limitations are acceptable for v0.2 because the release goal is visual
explanation, not full IDE-level debugging.
