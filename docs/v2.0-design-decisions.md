# Zero-CPU v2.0 Design Decisions and Limitations

This document records the architectural choices that define the Zero-CPU v2.0
release boundary.

It is intentionally about **why the current platform is shaped this way** and
what it deliberately does not attempt to be.

## 1. Platform Identity

Zero-CPU is a **verifiable and observable protected virtual computer platform**.

The project is not intended to emulate a commercial CPU or provide a
general-purpose operating system. Its purpose is to make important systems
boundaries small enough to inspect, execute, fault, trace, and verify end to end.

The v2.0 identity is:

> A small virtual computer where protection, multi-process scheduling, syscalls,
> devices, storage, debugging, and verification can all be observed in one
> execution flow.

## 2. Canonical Executable Path

The canonical execution path is:

```text
.zasm
  → Assembler
  → .zbin
  → Binary / Process Loader
  → process memory image
  → CPU fetch / decode / execute
```

`.zsym` remains a debug-symbol sidecar.

### Decision

The public architecture is based on real executable artifacts rather than an
in-memory instruction list.

### Why

This makes assembler output, executable format, loader behavior, process images,
runtime execution, debugging, and regression tests part of one coherent system.

Focused in-memory paths may remain for tests or compatibility, but they are not
the primary product story.

## 3. Core Owns Execution Semantics

```text
Core runtime / debugger
  ├─ zero_cli
  └─ Zero Studio
```

### Decision

CLI and Studio consume core/runtime/debugger behavior. They do not implement
independent machine semantics.

### Why

A second execution model in the UI would make debugger output difficult to trust
and would allow CLI, tests, and Studio to disagree about machine behavior.

Presentation state may live in Studio, but process execution, protection,
scheduling, syscalls, faults, and trace semantics remain below the frontend.

## 4. Explicit User / Kernel Protection Boundary

The protected host ABI is entered through `INT 80`.

```text
User
  → protected interrupt frame
  → Kernel
  → ProtectedSyscallDispatcher
  → validated service
  → return to User or terminate process
```

### Decision

Protected services are reached through an explicit privilege transition rather
than by giving User code direct access to host services or MMIO.

### Why

This makes the protection boundary observable and testable. The showcase can
demonstrate both:

```text
protected HW_WRITE succeeds
direct User-mode MMIO write faults
```

using the same hardware path.

## 5. Small, Independent Process State

Each process owns its own register state, PC/SP, memory image, execution ranges,
and lifecycle state.

### Decision

Process isolation is modeled explicitly even though the machine is intentionally
small.

### Why

The project can demonstrate a systems property that is more meaningful than
simple instruction execution:

```text
one process faults
→ only that process terminates
→ scheduler hands off
→ another process continues
```

The end-to-end showcase uses this as its central protection proof.

## 6. Simple Deterministic Scheduling

The current multi-process runtime uses round-robin scheduling with timer-driven
preemption.

### Decision

Use a deliberately small scheduler instead of adding priorities, multicore
scheduling, or complex policy.

### Why

The scheduling mechanism is sufficient to demonstrate:

```text
saved/restored process context
timer preemption
context switches
lifecycle handoff
survivor progress after a fault
```

while keeping traces deterministic enough for regression verification.

## 7. Minimal Protected Filesystem Surface

The v2.0 protected filesystem ABI is intentionally small:

```text
30  FS_STAT
31  FS_READ
32  FS_WRITE
```

ZeroFS is separate from the guest's 4 KiB RAM image, and filesystem request
blocks and guest buffers are validated before transfer.

### Decision

Use bounded path-based operations rather than building a general-purpose file
descriptor subsystem.

### Why

The v2.0 goal is to demonstrate the protected storage boundary, not to reproduce
a complete POSIX filesystem API.

This keeps the storage subsystem large enough to exercise real protected data
movement while avoiding unrelated filesystem expansion.

## 8. MMIO Abstraction with a Deterministic Mock Baseline

The hardware path is:

```text
Protected syscall
  → MMIOBus
  → HardwareMMIODevice
  → MockHardwareBus
     or SerialHardwareBus
```

### Decision

Use the mock hardware bus as the canonical v2.0 showcase and regression target.

### Why

The mock path is deterministic, reproducible, and available without external
hardware. The serial / ESP32 bridge remains useful as an optional physical
extension without making release verification depend on a specific board,
driver, cable, or host configuration.

## 9. Observability Is Part of Correctness

Zero-CPU records instruction, scheduler/context-switch, protected-syscall, fault,
and lifecycle information in structured execution observations.

### Decision

Verification is not limited to final register or console output.

### Why

Important claims are temporal:

```text
HW_WRITE happened before the fault
PID 2 faulted
scheduler handed off
PID 1 performed FS_WRITE after the fault
PID 1 exited normally
```

Those claims require execution history, not only final state.

## 10. Invariants and Golden Traces Serve Different Roles

The showcase is checked by both multi-process invariants and a deterministic
golden trace.

### Decision

Keep semantic invariant checks and trace regression together.

### Why

Invariants express architectural properties that should remain true even when
irrelevant details change. Golden traces catch unexpected changes in the
deterministic reference execution.

Using both gives stronger regression evidence than either mechanism alone.

## 11. Feature Freeze Is an Architectural Decision

v2.0 stops feature expansion after the end-to-end protected showcase.

### Decision

Productize and explain the implemented platform instead of adding more CPU,
filesystem, networking, or graphics features.

### Why

The project is strongest when a reviewer can understand and verify the complete
causal path:

```text
assembly
→ executable
→ process
→ preemption
→ protected service
→ protection fault
→ isolated termination
→ survivor completion
→ trace verification
```

Adding unrelated subsystems would make that story wider without making the core
systems claims clearer.

# Known Limitations

These are deliberate v2.0 boundaries, not hidden claims of completeness.

## CPU / Architecture

- Zero-CPU uses a custom ISA; it is not x86, ARM, RISC-V, or Linux compatible.
- The machine is designed for semantic clarity and verification, not cycle-level
  performance modeling.
- Cache, pipeline, branch-prediction, and speculative-execution simulation are
  outside v2.0.
- Guest RAM is intentionally small and fixed at 4 KiB.
- There is no paging, demand virtual memory, or hardware MMU model.

## Processes / Scheduling

- Scheduling is single-machine round-robin with timer preemption.
- There is no priority scheduler, multicore execution, SMP, or real-time
  scheduling policy.
- The process model is intentionally smaller than a production operating-system
  process model.

## Protected Runtime ABI

The protected host ABI is intentionally narrow:

```text
3   process exit
20  hardware write
21  hardware read
30  filesystem stat
31  filesystem read
32  filesystem write
```

It is sufficient for the protected showcase but is not intended as a complete
OS syscall surface.

## ZeroFS

ZeroFS is a deterministic protected-storage component, not a general-purpose
filesystem.

v2.0 does not provide:

```text
open / close file descriptors
permissions / ownership
symlinks
rename / delete API expansion
journaling
host filesystem mounts
network filesystem behavior
```

The release stops at the storage semantics needed to demonstrate protected
request validation and bounded guest/host data transfer.

## Hardware

- Mock hardware is the reproducible v2.0 release baseline.
- Serial / ESP32 transport is an optional physical extension and is not required
  for release acceptance.
- The hardware bridge exposes a deliberately small MMIO contract rather than a
  general device-driver ecosystem.

## Frontend / Host

- The full Studio and Windows serial experience targets Windows.
- Zero Studio is a debugger/presentation frontend over the core platform, not a
  separate virtual-machine implementation.
- The project does not target browser execution, GPU/3D rendering, or a Web
  platform in v2.0.

## Networking and Compatibility

- There is no network stack.
- There is no Linux/x86 compatibility target.
- Zero-CPU is not intended to boot existing operating-system binaries.

## Release Interpretation

A successful v2.0 release means:

```text
the documented protected virtual computer works as specified
the canonical showcase is reproducible
fault isolation is observable
the survivor completes
the trace satisfies invariants
the deterministic run matches the golden regression
```

It does **not** mean that Zero-CPU is a complete production CPU, operating
system, filesystem, or hardware virtualization platform.
