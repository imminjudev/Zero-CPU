# v0.3 Stack Trace Detail

This document describes the third Zero-CPU v0.3 debugger improvement.

## Goal

Studio already visualizes stack activity through the datapath canvas and
pipeline timeline.

This patch makes stack operations explicit in the Execution Detail Probe.

The debugger can now explain:

```text
PUSH R1
stack address = 2048
value = 60
SP = 2048 -> 2056
```

And:

```text
POP R3
stack address = 2048
value = 60
destination = R3
SP = 2056 -> 2048
```

## Important Stack Direction

Zero-CPU currently uses an upward-growing stack.

The implementation does:

```text
PUSH/CALL:
  Memory[SP] = value
  SP = SP + 8

POP/RET:
  SP = SP - 8
  value = Memory[SP]
```

So the default stack base `2048` moves to `2056` after one pushed 8-byte slot.

## Added TraceEvent Data

`TraceEvent` now includes `StackTraceDetail`.

The detail contains:

```text
active
operation
operand_text
destination
value
return_address
stack_address
sp_before
sp_after
target
has_value
has_return_address
has_stack_address
has_sp_change
has_target
is_push
is_pop
is_call
is_ret
note
```

## Supported Instructions

The first stack detail version covers:

```text
PUSH
POP
CALL
RET
```

For `PUSH`, it captures:

```text
- pushed operand
- pushed value
- stack write address
- SP before/after
```

For `POP`, it captures:

```text
- stack read address
- popped value
- destination register
- SP before/after
```

For `CALL`, it captures:

```text
- return address pushed onto the stack
- stack write address
- jump target
- SP before/after
```

For `RET`, it captures:

```text
- return address read from the stack
- stack read address
- final PC target
- SP before/after
```

## Studio Display

The `Execution Detail Probe` now includes a separate Stack Detail section.

Example:

```text
Stack Detail
  Active = true
  Operation = STACK_PUSH
  Operand = R1
  Stack Address = 2048
  SP = 2048 -> 2056
  Value = 60
```

For CALL:

```text
Stack Detail
  Active = true
  Operation = CALL
  Stack Address = 2048
  SP = 2048 -> 2056
  Value = 656
  Return Address = 656
  Target = 1000
```

## Why this matters

The old view answered:

```text
Did the Stack node become active?
```

The new view also answers:

```text
What value was pushed or popped?
Which stack address was touched?
How did SP move?
Where does CALL/RET control flow go?
```

## Current Limitations

This is still reconstructed from `TraceEvent` before/after snapshots.

Limitations:

```text
- It does not yet model stack operations as first-class CPU bus events.
- INT/IRET multi-slot stack behavior is not included in this first stack patch.
- Stack slot size is inferred from SP movement instead of exposed in StackTraceDetail.
```

This is acceptable for the third v0.3 patch because it makes PUSH/POP/CALL/RET
understandable without invasive CPU core refactoring.
